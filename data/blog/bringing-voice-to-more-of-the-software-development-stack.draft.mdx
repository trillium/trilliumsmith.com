I've been building toward the same thing from two directions. From one side: voice control of my machine. On my laptop that's Talon Voice, and I've pushed it far enough that firing a sanctioned action hovers around two fixed words, with a handful of core verbs at one. Something like `stow` captures a thought into my federated task and notes stores in a single utterance. It was not long ago that the baseline for the same action was ten to thirty words of prose, or switching to a terminal and typing it.

From the other side: AI agents that actually do the work. The problem there was never the agents. It was that everything lived in disconnected contexts I had to chase one by one, and whatever came out of a session sat still once the session ended. I've written before about that being the bottleneck — the human in the loop, not the agent.

This post is about the piece in the middle. Voice on one side, agents on the other, and the durable store between them that keeps a thought from evaporating when the conversation is over.

## The voice layer I already had

The Talon side is the part I can talk about most concretely, because it's measured. A set of voice plugins I run on my laptop give me one-utterance capture and fetch against my federated stores (`stow`), agent focus and messaging (`crew`), pane and tab navigation (`crew_nav`), and grabbing on-screen text by fragment (`snag`). The measured outcome was a median of two fixed words to fire a sanctioned action, one word for the core verbs, up from a ten-to-thirty-word baseline.

Voice also reaches my phone. Parlay, the small command server I built, takes any text as a command trigger, and on a phone the text comes from the device's own dictation — no custom speech engine, just the input method that already ships on the device. The flow is: dictate on the phone, the input box posts every edit to the command server, the server matches a command and routes the cleaned text to an agent, and the reply streams back down the same channel.

That part works. The part that didn't was what happened after the text stopped being text.

## The assistant as a connected client, not a chat island

The piece that made this click: stop treating the AI assistant as a fresh empty context every time, and give it read and write access to the same stores my other agents work from. Then the conversation is a refinement surface over the actual state of the work, not a bolt-on that guesses.

The assistant connects to my document store through a single MCP gateway. The gateway fronts a relay I built over my Beads store, which is a Dolt-backed, versioned, SQL-sourced document store with the markdown output as a derived human-readable render. The relay exposes a read/write tool surface: `project_resolve` for turning natural language into the right project, `capture` for cheaply persisting an idea or a friction point or a correction, `task_create_or_update` with duplicate detection, `dispatch_request`, and `verify` to check whether work someone is talking about already exists and where it's at.

The design rule I keep repeating, because it keeps the whole thing honest: the relay is a read/write communication and routing agent, never an executor. The stores are authoritative. The relay reads them, routes intent, and writes structured state or dispatch requests for external agents — and when current state matters, it polls the stores rather than keeping its own copy.

One practical lesson from running this: the assistant's view of the toolset goes stale. The gateway's bearer token is server-side only, never inside the assistant's own connection, and any change to the tooling wraps up with a refresh of the assistant's connector and a re-check of its tool list. Stale cache is the number one false bug.

## Write-back that outlives the conversation

Voice gets the thought captured; the store keeps it around. The next problem was the write path in the other direction: how the outcome of a conversation gets written back into the store without manual surgery.

On the Beads side, the write path is a CLI call, never a raw file write — agents write through the store's own interface, and humans browse the derived markdown in Obsidian.

On the ChatGPT side, I built a parser for the after-action of a conversation. The assistant lays out what it thinks a bead should say as a `## {bead-id}` section in a pasted inbox block, and the inbox bead is labeled `source:paste`. The parser validates that the bead id exists, rejects mismatched ids, preserves the surrounding bead fields, hash-checks before and after, and applies the wording as UNCONFIRMED — never auto-confirmed, always with a provenance comment. The acceptance test was: pasted write-back flows inbox to bead update without manual text surgery.

## Inbox beads are the handoff

The moment a capture is a bead in a store, handing it off gets boring in the good way. An inbox bead is assigned to a worker, decomposed into sequenced child tasks, and dispatched to an execution agent — with dispatch held on gating where needed, and the bead staying open until the outcome actually lands. This post is a live example: it started as an inbox bead, got dispatched to a worker on its own branch, and stays open until the PR lands.

The same shape applies to decisions. A "this needs your review" is a durable, gated item in its own queue rather than a sentence in a chat — so it doesn't evaporate when you look away.

The loop, as I've written it down: note in, bead filed, delegate, execute, report, and link back to the originating note.

## Choosing what gets seen and what gets said

One habit from my streaming setup: a "Private" OBS scene that covers the desktop during sensitive operations — typing API keys, editing env files, password prompts — bound to a Talon voice command and a hotkey for an instant swap. And on the input side, I've noted that some mediums give weaker visual feedback than a laptop (the phone being the big one), so those mediums should lean on auditory feedback to compensate.

## Extending voice further down the stack

The pattern extends past capture. My Talon setup is itself exposed as MCP tools — `talon_mimic`, `talon_restart`, `talon_getScope`, `talon_getRecentLogs` — which means agents can drive the voice layer the same way they drive anything else, through plain subprocess calls. Voice commands already reach the terminal multiplexer. There's a voice-driven prose review loop where a single command opens a review session for rewriting text one at a time.

The end state I'm heading for: the voice surface, the agent, and the store all read and write the same thing, so a thought can go from spoken to stored to executed without me restating it at each hop.

## Honest caveats

Everything here is alpha, single-owner, and built around my exact workflow. The gateways, the relay surface, the write-back parser, the voice plugins — they work for me daily, and several are still changing under me. If some of this reads like a chain of taped-together experiments, that's because it is. That's also why it's worth writing down: the pieces are generic enough that the pattern — voice in, durable store in the middle, agents out the other side — is the part that should age well.
