Hey folks

I have been using an extension of beads for the last 7 months, I thought it was a good use case and wanted to share and hear your thoughts

### The problem

I wanted agent native tools to be a personal information tracker, with the ability to store my thoughts big or small at any time. Beads was the right shape but was limited to a single project or domain, I wanted it to grow to take over any agent based record that needed to be saved

### The solution

One database with multiple prefixes per domain type, allowed to interconnect in any way necessary.

Brain: Beads as a domain based task store

One database, many named stores eg "task, brain, robot, status, project"

I've been using this and am up to roughly 20,000 beads, some manually generated and others generated as part of tool errors or misbehaving agent actions that need resolution. Agents are empowered to use the tools to record problems, and make new stores if they see fit.

Three kinds of bead, because "generated" hides a difference:

- Procedural: a formula writes it, fixed title shape, no judgment (session trails, guard hook decisions, dispatch "State change" records, pane-blocked alerts).
- Agent-authored: an agent wrote real content under instruction (findings, tasks, handoffs, ChatGPT-by-voice captures).
- Human-authored: I typed it.

As of 2026-10-22, of 31,001 beads: 56% procedural, 10% test pollution, 8% marked agent-authored, 27% unmarked (me or an agent at my CLI, which the data can't separate). So human-authored is at most 27%.

### How I've been using it

I've been using Brain as a project management and documentation store. Generalized abilities are P0 beads (eg agent orchestration), an instance of that ability is a P1 bead (Gastown would be here -- other examples)

This lets me create dependencies across projects and scopes , creating links to knowledge, or tasks that need to be done.

### The productivity unlock

Exposing beads to an mcp tool lets me use chat gpt by voice, discuss and curate tasks, then launch them via trigger a build request to a primary agent like The Mayor of Gastown or Firstmate.

### Features on top of beads

A snapshot of additional features on top of beads (each with an example command and why; "proposed" means the command shape I would want, not confirmed to exist):

- Canonical registry that drives the binary and one command per store
  - Command: `brain stores list`
  - Why: one file is the source of truth, so a new store gets its command, prefix and export folder with no hand wiring.

- Cross-store search
  - Command (proposed): `brain search "oauth" --all-stores`
  - Why: I rarely remember which store holds a thing, and one query across all of them replaces guessing.

- Idempotent store creation
  - Command: `brain stores create travel`
  - Why: agents can make a store when a domain needs one, and running it twice does no harm.

- Markdown export of every change
  - Command (proposed): `brain export --store task --since yesterday`
  - Why: every store has a readable, diffable record outside the database, good for backup, review and grep.

- Self-describing ids (the prefix names the store)
  - Command: `task show task-q1k8`
  - Why: the id alone says where the bead lives, so a pasted id never needs a "which store?" question.

- A kind label: task, knowledge, both, isa
  - Command (proposed): `brain create "Gastown notes" --kind knowledge`
  - Why: a store holds both work and facts, and the label lets me filter to just things to do or just things to know.

- Routing doctrine (is it something to DO or something to KNOW)
  - Command: `task create "Fix the nudge text"` versus `brain remember "How the nudge picks its text"`
  - Why: one question decides the store, so agents file things the same way every time and misfiles are easy to spot.

- Failure stores: robots, violations, errors, friction
  - Command: `robots create "hook misfired on cd"`
  - Why: problems are recorded where they can be counted and fixed, instead of being worked around silently.
  - Note: these are agent-authored (an agent noticed and wrote it up). lifespan and guard are the procedural stores, written by formula rather than judgment.

- A human label that sends an item to my review queue
  - Command: `brain tag brain-ow1w human` then `brain human list`
  - Why: only the hard calls reach me, and they all sit in one queue I can clear in a batch.

- lifespan, handoff and dump for session trails
  - Command: `handoff create "Session close: Sidecar deployed, next is panel columns"`
  - Why: a new session starts from the record, not from memory. lifespan logs automatically, handoff is a deliberate close, dump catches a cut-off one.

- The beads-bridge MCP server, with a live dashboard
  - Command: open the bridge's /live page in a browser
  - Why: ChatGPT by voice can read and write every store, and the dashboard shows each tool call as it happens, so I can see what the agent did.

### Numbers (live count)

- 26,088 beads across 61 prefixes, since 2026-03-18 (about 7 months). 18,543 open, 7,485 closed. 9,284 comments, 5,621 links between beads.
- About 12,100 are machine-generated: lifespan (7,390, one bead per agent session, written automatically) and guard (4,740). About 14,000 were written deliberately.
- Recount 2026-10-22 (31,001 beads): 17,220 procedural, 3,049 test pollution, 2,342 marked agent-authored, 8,390 unmarked. Procedural also covers 3,893 task "State change" records, 416 pane alerts and the hook-captured rows in brain.
- The record doesn't store who wrote a bead (the author field is the git user name on 28,318 of them), so the human share is an upper bound until a provenance field exists.
- task is the busiest authored store: 6,725 total, 958 created in the last 7 days.
- About half of task is procedural bookkeeping (3,893 "State change" and 416 pane-alert beads out of 8,570 task beads today), so the busiest store by hand-authored work is smaller than that count suggests.
- robots (agent-detected tooling defects): 1,096 recorded, 211 in the last week.
- inbox: 570 captured, 6 still open.

### Differences from beads

- Shape: one shared Dolt server, one database per store, one prefix per store, one markdown export folder per store.
- Brain is a Go fork of beads that changes the unit of ownership from the repository to the domain.
- A new store is warranted only when a domain needs its own prefix, namespace and export root (`brain stores create`).
- Cross-store links are `project:<name>` and `resume:<slug>` labels.

### Honest costs

Rebase maintenance against upstream, divergent release lines, README drifting from the registry.

Also: no per-bead record of who or what wrote it, so human versus agent versus procedural has to be inferred from store names and labels, and about 10% of the store is test pollution.
